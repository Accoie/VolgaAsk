# VolgaAsk

Чат по нормативным документам Волгатеха. React отправляет вопрос в ASP.NET Core. API проверяет сессию и владельца чата, вызывает Python RagService и передаёт токены модели в браузер по SSE. После успешной генерации API сохраняет вопрос и полный ответ одной транзакцией.

| Компонент | Назначение |
|---|---|
| `Frontend/` | Чат на React и TypeScript, история, регистрация и управление пользователями |
| `Backend/` | ASP.NET Core 8, EF Core, FluentValidation, аутентификация и Swagger |
| `RagService/` | Поиск в pgvector, ранжирование, генерация в Ollama и индексация PDF |
| `DocumentGenerator/` | Подбор шаблона, диалог и формирование DOCX |
| `DocumentReview/` | Обезличивание, локальная проверка и анализ в GigaChat |
| PostgreSQL `app-db` | Учётные записи, чаты, состояния анкет, метаданные версий и отчёты |
| PostgreSQL `pgvector` | Текстовые фрагменты документов, метаданные и эмбеддинги |

## Запуск в Docker

Из корня репозитория. Для первого запуска скопируйте `.env.example` в `.env`, если файла ещё нет. Задайте `APP_DB_PASSWORD`, `ADMIN_LOGIN` и `ADMIN_PASSWORD` (10–128 символов). Администратор создаётся при первом запуске с пустой БД. Изменение пароля в `.env` у существующего аккаунта пароль не сбрасывает.

```powershell
docker compose up -d --build
docker compose logs -f rag
```

Чат доступен по адресу [localhost:8080](http://localhost:8080), Swagger UI — [localhost:8080/swagger](http://localhost:8080/swagger). Порт задаётся через `WEB_PORT`. При первом запуске нужны интернет и место для образов и весов моделей. Compose использует существующие тома проекта `ragservice`, запускает Ollama и при необходимости загружает `qwen2.5:3b`. На компьютере без NVIDIA используйте `docker compose -f docker-compose.yml -f compose.cpu.yml up -d --build`.

Корпус документов находится в `RagService/data/raw`. Чат использует подготовленный поисковый индекс.

## Роли

При обновлении существующей базы прежний идентификатор становится логином. Пароль и история сохраняются. Существующие аккаунты получают отображаемое имя «Пользователь» или «Администратор».

| Роль API | Доступ |
|---|---|
| `User` | Вход, собственные чаты, история и вопросы |
| `Employee` | Собственные чаты, история и вопросы |
| `Admin` | Также создание учётных записей и изменение ролей |

Логин содержит от 3 до 64 латинских букв, цифр или знаков `.`, `_`, `-`. Пароли обрабатывает ASP.NET Core `PasswordHasher`. Пользователь регистрируется по логину, имени и паролю через «Создать аккаунт» и сразу попадает в чат. После индексации в pgvector остаются фрагменты и векторы.

## Проверка через Swagger

1. Откройте Swagger и выполните `POST /api/auth/login` с полями `login` и `password` из локального `.env`. Браузер сохранит сессионную cookie. `GET /api/auth/me` покажет активную роль.
2. Для самостоятельной регистрации выполните `POST /api/auth/register` с полями `login`, `name` и `password`.
3. Выполните `POST /api/chats`, скопируйте `id` и подставьте его в `POST /api/chats/{id}/messages`. Пример тела — `{"question":"Кто избирает ректора?"}`. Ответ имеет тип `text/event-stream`. События `token` содержат фрагменты текста, `done` подтверждает сохранение, `error` сообщает о сбое. Swagger показывает тело после завершения, в чате текст появляется по мере генерации.
4. Выполните `GET /api/chats/{id}/messages` и проверьте сохранённую пару вопрос–ответ. Удалить свой чат можно через `DELETE /api/chats/{id}`. Чужой идентификатор чата возвращает `404`.
5. Через `POST /api/accounts` создайте пользователя или сотрудника, указав `login`, `name`, `password` и `role`. Выполните `POST /api/auth/logout`, войдите новой учётной записью и повторите проверки доступа. Запрос без входа возвращает `401`, действие вне роли — `403`.

Описание исходного поискового модуля находится в [RagService/README.md](RagService/README.md).

## Заявления в чате

В режиме «Автоматически» чат выбирает между справочным ответом и оформлением заявления. Например, после вопроса о баллах можно написать «Хочу материалку оформить». DG предложит бланк, соберёт поля и покажет сводку. На этом шаге можно указать исправления или подтвердить создание DOCX.

После подтверждения и создания DOCX сервис обезличивает копию, проверяет её локальной Qwen и при успешной проверке автоматически передаёт в GigaChat. Настройки внешнего API берутся из `DocumentReview/.env` по образцу `DocumentReview/.env.template`. В карточке готового документа доступны предпросмотр оформления DOCX, скачивание оригинала и доработка. Каждое подтверждение исправлений создаёт отдельную версию.

`storage/catalog/templates` заполняется штатными шаблонами при первом запуске генератора. После изменения шаблонов перезапустите сервис `generator`. Оригиналы лежат в `storage/<UUID чата>/<UUID файла>.docx`. Для резервной копии сохраните каталог `storage` и базу `app-db` вместе. На Linux процесс API (UID 1654 в образе .NET) должен иметь право создавать каталоги в `storage`.

В Swagger используйте прежний маршрут `POST /api/chats/{id}/messages`. Поле `mode` принимает `auto`, `question` или `document`. Для исправления конкретной версии передайте её `fileId` в `reviseFile`. История сообщений содержит идентификатор, название, текст превью и результат проверки. Оригинал доступен владельцу через `GET /api/chats/{chatId}/files/{fileId}`.
